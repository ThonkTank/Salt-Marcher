# Repository instructions

- This project has no production users or production data requiring preservation.
- Development data is disposable. Schema migrations and backward compatibility are not required; choose the simplest coherent implementation for the authorized work.
- Preserve unrelated working changes and files. Do not delete unrelated files, reset the working tree, or overwrite existing work.
- The active desktop editor is Atlas V7. Its architecture and the pure house-local interior solver are described in `docs/architecture.md`; observable behavior, persisted format and limits are defined once in `docs/product-contract.md`.
- Exactly four authoritative product/development documents are maintained: `README.md` (setup and commands), `docs/architecture.md` (ownership and implementation), `docs/product-contract.md` (behavior), and `docs/implementation/status.md` (latest checked state, decisions, open limits and next handoff). Consult the documents relevant to the task; generated evidence and plans are not runtime contracts.
- `legacy/pre-atlas-v7/` is historical reference, not current guidance or a product contract. Read it only when a concrete task requires historical evidence and state that reason; do not include it in the default reading path. Preserve the archive; do not delete it as cleanup.
- The user-requested durable Atlas rebuild assignment is `docs/implementation/atlas-rebuild-plan.md`. When asked to execute that plan (including a reference plus "erledige das"), carry out its full P0–P9 scope and completion criteria. It describes the intended future state, not implemented behavior. Keep this one execution plan versioned and linked; do not create parallel plans or reports. Unrelated tasks do not activate the rebuild.
- Replace the short current status when work changes the checked state. Record detailed check logs and temporary plans under ignored `src-tauri/target/cleanup/` or `src-tauri/target/diagnostics/<run>/`; do not add historical reports, screenshots, raw data, source copies or builds to `docs/`.

## Problem solving and verification

Use the following for substantial, uncertain or previously unsuccessful work; keep small, obvious changes lightweight.

- Own diagnosis, technical decisions, implementation and verification. The user provides goals and symptoms; do not require them to propose solutions, design tests or repeatedly request review. Ask only for a missing product decision, access or information that materially blocks progress.
- Derive observable acceptance criteria from the user goal and product contract. Reproduce the reported action in the relevant application and build mode, and capture a comparable baseline. Functional test passes, event counts and reduced internal work do not establish user-visible performance.
- Validate new or materially changed acceptance checks against relevant known-bad and known-good cases. Confirm that failures occur for the intended reason; use targeted fault injection in isolation when needed. Missing measurements and unrelated test failures do not validate a check.
- Before substantial optimization, use measurements to identify the bottleneck and state a testable cause and expected effect on the complete user action. If the current approach cannot plausibly reach the target, compare structural alternatives. Test the riskiest assumption with a small representative implementation before a broad redesign.
- Set a proportionate experiment budget before pursuing an uncertain approach. Continue while results improve the user outcome or resolve a named uncertainty that changes the next implementation decision. Reassess diagnosis, measurement and architecture when the budget is exhausted or progress plateaus; renew the approach only with a changed, evidence-based rationale. Do not automatically rewrite or keep accumulating minor edits.
- Use additional reviewers only when they can resolve a concrete uncertainty. Resolve supported findings or rebut them with evidence. Judge reviews by useful findings and regressions, not agreement or number of objections. Avoid mandatory review rituals, redundant test runs and invented defects.
- Claim completion only with relevant evidence from the final state. Report measured results and remaining validation gaps; do not claim a symptom is fixed without verifying the relevant behavior or make the user the routine final tester. Use the existing status and evidence locations above.
- Before adopting substantial new workflow requirements as defaults, compare representative known failures and simple control tasks under comparable conditions and budgets. Assess outcomes, regressions, unnecessary work and cost. Retain additions only when their benefit justifies the overhead.

## Code health and architecture boundaries

- Give each mutable state one owner. Derive UI status from that owner; do not introduce parallel journals, history stacks or competing saved/loading flags. Durable edits use the existing change, history, invalidation and persistence lifecycle.
- Keep domain calculations independent of UI, rendering and storage adapters. Coordinators sequence work; domain modules calculate results. A state owner may delegate to cohesive modules without transferring ownership.
- Each function should have one concrete, cohesive task at one abstraction level, describable by its result or invariant in a short sentence. Split independent responsibilities or mixed abstraction levels when this improves understanding or dependencies. Do not split merely to meet a line limit, add ceremonial comments to every function, or scatter an atomic state transition across helpers.
- Async work must define document/version identity, acceptance and completion conditions, cancellation and resource release. Accepted, applied, persisted, GPU-complete and visibly presented are distinct states. Preserve accepted edits across UI lifecycle changes.
- Derived data must remain reconstructible. New long-lived caches require an owner, complete identity, invalidation, budget and release lifecycle, justified by measured need. Local edits should perform work bounded by affected data; verify relevant scaling when changing access paths.
- Run `npm run check:architecture` when changing module dependencies or its guards. It enforces the boundaries documented in `docs/architecture.md`; generated transport contracts remain covered by `contracts:check`. Validate guard changes with known-good and deliberately failing examples. Do not weaken a guard, add an exemption or change a behavioral expectation merely to make a failing change pass; explain any intentional contract change and retain a regression check for the underlying risk.
- For substantial changes, review ownership, dependency direction and failure/cancellation behavior with proportionate behavioral checks. These are review questions, not a mandatory report or a request to refactor unrelated code. Experiments need a bounded purpose and a criterion for adoption or removal; share abstractions only when semantics actually coincide.
